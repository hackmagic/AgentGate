# 05 · Behavioural event specification

English | [中文](../zh-cn/05-event-spec.md)

This is the contract for the source-data layer. It does not invent a new capture format; it defines a
semantic superset that stays compatible with existing ActivityWatch and screenpipe fields.

## Event shape

```yaml
event:
  id: uuid                      # generated by the adapter when absent
  type: focus_block_started     # see the table below
  timestamp: ISO8601
  source: activitywatch | screenpipe | manual
  context:
    app: string                 # required
    project: string | null
    language: string | null
  duration_seconds: number | null
  metrics: {}                   # numeric observations such as focus_score
  metadata: {}                  # adapters may keep raw fields here; the engine must not depend on them
```

`metadata` is the escape hatch: adapters put raw ActivityWatch fields there, and **the engine never
reads it**. That keeps debugging information while preventing a policy from quietly depending on an
unspecified field.

## Event types

| Type | MVP | Semantics |
| --- | --- | --- |
| `focus_block_started` | ✅ | Entering a continuous focus block |
| `focus_block_ended` | ✅ | The focus block ended |
| `app_switch` | ✅ | Foreground application changed |
| `idle_detected` | — | The user left (AFK beyond a threshold) |
| `interruption` | — | Interrupted by something external |
| `notification_received` | — | A notification arrived |

The last three are already in the schema and the policy DSL so adapters can report them early; the
bundled MVP adapter simply does not generate them.

## ActivityWatch adapter rules

Entry point: `eventsFromActivityWatch(input, options)`, accepting a bucket array,
`{ buckets: [...] }`, or a single bucket.

| Option | Default | Semantics |
| --- | --- | --- |
| `focus_block_minutes` | 25 | A run of one app must last this long to count as a focus block |
| `gap_tolerance_seconds` | 120 | Adjacent rows closer than this belong to the same run |
| `idle_minutes` | 5 | An AFK row must last this long to become `idle_detected` |

Emission rules:

1. Sort window rows by `timestamp` and merge them into runs per `app` (gaps ≤ `gap_tolerance_seconds`);
2. An `app` change → emit `app_switch` (`metadata` carries `from_app` / `to_app`);
3. A run at least `focus_block_minutes` long → emit a `focus_block_started` / `focus_block_ended` pair, where `duration_seconds` is the **whole block duration**;
4. An AFK row with `status: afk` lasting at least `idle_minutes` → `idle_detected`.

### Extracting project / language

Deliberately conservative: **return `null` when unsure**, rather than guessing a value that might
silently loosen a policy.

| Application | Rule |
| --- | --- |
| VS Code family (`Code`/`Cursor`/`Windsurf`/`VSCodium`) | Split the title on ` - `; with at least 3 parts take the second to last |
| Terminal family (`Terminal`/`iTerm2`/`WezTerm`/`PowerShell`…) | Extract a path from the title and take the final directory name |
| Anything else | `null` |

`language` is mapped from a file extension in the title (`ts`→`typescript`, `rs`→`rust`, …), and is
`null` when nothing matches.

## Acceptance criteria

> Given an ActivityWatch export JSON, the adapter produces a valid event sequence, and the
> `focus_block_started` rule has unit test coverage.

Location: `tests/adapters.test.ts`

- The sample export → 7 ordered events, with every field asserted
- Two 10-minute runs do not form a 25-minute focus block; lowering the threshold merges them
- Short AFK rows are ignored
- A non-ActivityWatch payload → `invalid_activitywatch_export`
- `normalizeEvent` fills defaults and rejects unknown types

## Relationship to the pet and MCP

Events are **the engine's input**, not the pet's input. The pet only ever sees a `GateSignal`; an agent
submits events through the MCP `gate/evaluate` tool. This boundary keeps the pet from becoming "a
monitor that watches raw behaviour directly".
