# 07 · Embodiment interface specification

English | [中文](07-pet-bridge.zh.md)

The pet is not the agent's skin. It is the embodiment layer for a `GateSignal`. The interface is
defined between the engine and the pet runtime, decoupled from any specific implementation
(dsh-pet / OpenPets / anything else).

## Engine → pet: `gate_signal`

```yaml
id: uuid
policy_id: string
decision: suggest | require_approval | suppress        # note: never allow
presentation:
  animation_hint: idle_shift | stretch | alert | thinking
  bubble_text: string          # at most 30 characters, from the policy
  actions:
    - label: Approve
      action_id: approve
    - label: Ignore
      action_id: dismiss
    - label: Silence for 1 hour
      action_id: mute_1h
action:                        # declared intent, not an executed action
  type: suppress_notifications
  scope: [slack, mail]
  parameters: { duration_minutes: 50 }
escalation:
  after_minutes: 10
  action: remind_once
  decision: suggest
expires_at: ISO8601 | null
created_at: ISO8601
trigger_event_id: string       # for tracing; contains no window content
audit_level: full | summary | none
```

Schema: `schemas/signal.schema.json`. Invariants are enforced at construction by `validateSignal()`:

- `bubble_text` is at most 30 code points (CJK counts as one character);
- `decision: require_approval` must offer at least one non-`approve` action — **refusal must be possible**.

## Pet → engine: `gate_response`

```yaml
signal_id: uuid
action_id: approve | dismiss | mute_1h
responded_at: ISO8601
```

Only these three actions are legal. A pet cannot invent actions, and it cannot answer with just a
`policy_id`: it must return the exact `signal_id` that was presented, or the engine raises
`unknown_signal`.

## Interaction constraints (fixed, so a pet cannot become a nuisance)

1. One policy is presented at most once per `escalation.after_minutes` window (default 30 minutes);
2. No automatic retry after a user `dismiss`;
3. The pet must not pop up unprompted while the user is in a `focus_block` with no matching policy;
4. Every `require_approval` signal must include at least one "refuse" action;
5. Pet animation and bubble copy **must not be generated by an LLM at runtime**; they come from the policy's `presentation` field, which keeps them auditable and testable.

Constraints 1 and 2 are implemented by the `AgentGate` rate limiter and `mute` state machine;
constraint 4 by `validateSignal`; constraint 5 by there being no generation entry point in a signal at
all.

## HTTP bridge (`gate pet`)

Listens on `127.0.0.1:3778` by default and binds loopback only.

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/healthz` | `{status, engine_version, policy_count}` |
| `POST` | `/v1/events` | body `{event}` (a bare event is also accepted); returns the evaluation result |
| `GET` | `/v1/signals/pending` | Unanswered, unexpired signals |
| `POST` | `/v1/signals/:id/respond` | body `{action_id, responded_at}` |

Errors are returned as `{error: {code, message, retry_after_seconds?}}`:

| Status | Situation |
| --- | --- |
| 400 | Malformed event or response body, or a JSON parse failure |
| 404 | Unknown `signal_id`, or the signal does not offer that action |
| 429 | Event submission rate limited (60 per minute by default) |

Tests override the server clock with the `X-Agent-Gate-Now` header. It drives the evaluation instant
(`time_window` / `day_of_week`), the rate limiter and expiry alike, so replaying historical events is
reproducible.

## Wiring a pet host

Use the host's `apply` entry point and HTTP routing table to map the engine's `gate_signal` onto the
pet's existing bubble and animation pool. Do not modify the pet core; write an adapter plugin.

Minimal adapter shape:

```ts
// Pseudo-code: a plugin on the pet side
import { apply } from 'dsh-pet/host';
import { PetBridgeClient } from 'agent-gate/pet';

apply((host) => {
  const client = new PetBridgeClient({ baseUrl: 'http://127.0.0.1:3778' });

  client.onSignal((signal) => {
    host.bubble.show(signal.presentation.bubble_text);
    host.animation.play(signal.presentation.animation_hint);
    host.buttons.render(signal.presentation.actions, async (actionId) => {
      await client.respond(signal.id, actionId);   // report only, never execute
    });
  });
});
```

The key point: **the pet never silences notifications itself.** It sends the `action_id` back, and a
user-space adapter (or the agent host) performs the action — the engine only records the decision and
the response.

## Acceptance criteria

> Trigger a `require_approval` policy by hand; the pet shows the prompt, and after the user approves,
> the audit log records the whole chain.

Location: `tests/pet.test.ts`

- Initial `healthz` / `pending` state
- Event → signal → visible in `pending` → `approve` → `pending` empty
- After `dismiss`, the same policy does not retry (`throttled: true`)
- Unknown signal 404, bad JSON 400, rate limit 429
